Diffusion from scratch · Apple MPS

Cats, dogs, and one Australian Shepherd

Two models, one repo. A class-conditional DDPM trained from scratch on pet photos, and a pretrained latent-diffusion model for the breed prompt the scratch model structurally cannot answer. Plus four bugs that were quietly ruining the output.

The requested prompt

RealVisXL V4.0 at 1024×1024, 35 denoising steps, guidance 7.0, with a photographic negative prompt. ~90 s per image on MPS. Blue merle coat, tricolour markings, the characteristic face mask, real depth of field and individual fur strands.

Getting to photorealism

The first pass used sd-turbo and looked illustrated. The cause was not the prompt — it was guidance. Turbo models are distilled to run in 4 steps with guidance_scale=0.0, and at zero guidance a negative prompt is mathematically inert: there is no unconditional prediction to push away from. So no amount of "photorealistic, not a painting" could take effect.

Why this needed two models

The from-scratch UNet cannot take a breed prompt. It is conditioned on an nn.Embedding over class indices — there is no text encoder and no cross-attention, so the only things it can be asked for are labels it saw in training.

"Australian Shepherd" is also absent from every credential-free labelled pet dataset: Oxford-IIIT Pet has 37 breeds, Stanford Dogs has 120, and neither includes it. So the breed prompt goes to a text-conditioned model, and the scratch model is judged on breeds it can actually see.

From scratch — this repo

14.3M-parameter UNet, cosine noise schedule over 1000 steps, EMA weights, classifier-free guidance, DDIM sampling. Conditioned on 2–37 integer class labels. Trained on 380 images for ~76 minutes.

Pretrained — sd-turbo

~1B parameters, latent diffusion with a CLIP text encoder and cross-attention, distilled to 4 steps. Trained on billions of captioned images at a cost of millions of GPU-hours. Inference only here.

Bugs the samples exposed

The loss curve looked healthy while every sample came out as coloured speckle. That gap is diagnostic: training was fine, sampling was broken.

1. The predicted x₀ was never clipped

Sampling starts at t=980, where sqrt(alphas_cumprod) ≈ 0.03. Recovering x₀ divides by that, multiplying any noise-prediction error by ~32. With no clamp, the x₀ estimate left [-1, 1] by an order of magnitude on the first steps and never came back.

Fixed in both samplers. The DDPM path was rewritten to build its posterior mean from the clipped x₀ using the posterior_mean_coef buffers the class already registered — verified algebraically identical to the original closed form to 3e-13 in float64.

2. Early stopping threw away 300 epochs

The first full run halted at epoch 335 — and the checkpoint it kept was from epoch 34. Two compounding causes: max_patience was num_epochs // 4 = 300, and best-checkpoint selection tracked validation noise-MSE, which on a 20-image split is almost pure noise, so it latched onto a lucky early epoch and never beat it.

Early stopping on validation loss is simply the wrong tool for a generative model: sample quality keeps improving long after that number plateaus. Diffusion models are normally trained to a fixed step budget, keeping the latest EMA weights. So early stopping is now off by default (--patience 0) and the latest weights are always written to model_last.pth beside the best-val model.pth.

3. DataLoader workers re-spawned every epoch

Without persistent_workers, every epoch pays macOS process spawn. On a 380-image dataset an epoch is ~12 optimizer steps, so 9 of every 11.6 seconds were spawn overhead. Setting it cut the epoch to 3.8 s — a 3× speedup that bought 3× the training steps in the same wall clock.

And a fourth, smaller: inverse_normalize was a lambda stored on the dataset, which made it unpicklable and crashed any run with --num-workers > 0.

Augmentation was blocking the overfit check

The goal was a memorisation check: train two visually opposite breeds until the model reproduces them, proving the pipeline end to end. It would not converge to anything recognisable, and the dataset was the reason.

RandomResizedCrop, RandomHorizontalFlip and ColorJitter ran on every load, so the model never saw the same image twice. That is correct for generalisation and precisely wrong for memorisation — augmentation effectively enlarges the dataset, which is the opposite of what an overfit test needs.

Two flags now exist for this. --no-augment makes loads deterministic (verified bit-identical across reads). --repeat N presents the split N times per epoch: 64 images at batch 32 is 2 optimizer steps, so per-epoch validation and report writing cost more than the training itself — --repeat 8 makes it 16 steps per epoch instead.

Throughput on MPS — why 32×32

Measured, not guessed. The 64px config could reach only ~3.6k optimizer steps per hour; DDPM results are usually quoted at 100k+ steps, so resolution had to give way to step count.

Self-attention at the 32×32 feature map is the expensive term — 1024 tokens per head. Standard DDPM applies attention at 16×16 only; the repo was doing both, so it is now behind --attention-resolutions.

More sampling steps made it worse

Counterintuitive, and measurable. Sampling the same weights at increasing DDIM step counts steadily drains contrast — the images wash out toward flat grey.

The cause is the interaction between clip_denoised and an undertrained model. Every step re-projects the x₀ estimate back into [-1, 1]; when that estimate is poor, each projection pulls slightly toward the mean, and more steps means more contractions. Clipping is still necessary — without it the samples are pure speckle — but with these weights the sweet spot is 25–50 steps, not 200. A better-trained model would not contract like this.

Where the shortfall actually is

Reconstruction quality per noise level, measured on held-out images. The model recovers x₀ almost perfectly from lightly noised inputs and badly from heavily noised ones — and DDIM sampling starts at t=980. That is the signature of too few optimizer steps, not a broken sampler.

Reproduce

The dataset downloads itself — 792 MB, no credentials, no Kaggle account.

# memorisation check: small set, augmentation OFF, no early stopping
python train.py --breeds samoyed,pug --epochs 600 --image-size 32 \
  --attention-resolutions auto --no-augment --repeat 8 --max-samples 64 \
  --ema-decay 0.999 --label-dropout 0.1 --num-workers 0 --patience 0 \
  --output-dir outputs/overfit64

# sample a breed the checkpoint knows about (model_last = latest weights)
python sample.py --checkpoint outputs/overfit64/model_last.pth \
  --class-name samoyed --num-samples 8 --cfg-scale 3.0 --sample-steps 100

# all 37 breeds (needs many more steps than one laptop hour)
python train.py --epochs 200 --image-size 32 --attention-resolutions auto

# photoreal text prompts (RealVisXL is the default model)
python text2image.py --prompt "RAW photo of an australian shepherd dog in a meadow, 85mm lens"

# fast but illustrated-looking, for iterating on prompts
python text2image.py --prompt "a photo of a tabby cat" --model stabilityai/sd-turbo

What would actually move the needle

  • More steps, by a lot. This run is ~9.6k optimizer steps. Published 32×32 DDPM results use 300k–800k, and the diagnostic below shows exactly where the shortfall bites. Overnight is the single biggest win available.
  • Then resolution. 64px only makes sense once 32px is converged; it costs 5× the time per step.
  • Fine-tune instead of train. The repo already has --freeze-policy. Adapting pretrained weights beats from-scratch on this hardware for any real image quality.
  • Breed prompts need text conditioning. Swapping the class nn.Embedding for a text encoder plus cross-attention is the architectural change that would let one model answer "Australian Shepherd" — and it needs captioned data, which Oxford Pets does not have.
